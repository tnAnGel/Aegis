# 架构

**语言：** **中文** · [English](../en/02-architecture.md) · [Русский](../ru/02-architecture.md)

## 进程模型

Aegis 以 **N 个单线程工作进程**运行，每个 CPU 核心一个，并通过 `CPUAffinity=%i`
与核心 1:1 绑定；所有进程通过 `SO_REUSEPORT` 监听同一组端口。内核按四元组哈希把
连接分配给某个工作进程，因此没有共享的 accept 锁，也没有跨核惊群。

```
                 :80 / :443 (SO_REUSEPORT)
   ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
   │ w0   │ w1   │ w2   │ w3   │ w4   │ w5   │ w6   │ w7   │   systemd 模板单元
   │ cpu0 │ cpu1 │ cpu2 │ cpu3 │ cpu4 │ cpu5 │ cpu6 │ cpu7 │   aegis-pingora@N
   └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
              共享内存：计数器、信誉、限流状态
```

`systemctl restart aegis-pingora.target` 会扇出到所有实例；滚动重启则逐个重启工作
进程，使监听套接字集合始终非空。

权衡：thread-per-core 布局在实测中更快（RPS 更高、负载下 p99 更低），代价是内存——
每个工作进程都是一份完整的进程镜像。工作进程数量可在安装时指定，也可以在面板的
**Workers** 页面调整。

## 请求流水线

```
   数据包
     │
     ▼
 ┌─────────────────────────────────────────────────────────┐
 │ XDP / eBPF（内核态）  拒绝表 · 放行表 · SYN 预算        │  ← 根本不进入用户态
 └─────────────────────────────────────────────────────────┘
     │
     ▼
 ┌─────────────────────────────────────────────────────────┐
 │ TLS 握手       JA3 · JA4 · JA4S/T/L/X · GREASE          │
 │                SNI 路由 · mTLS · 票据密钥               │
 └─────────────────────────────────────────────────────────┘
     │
     ▼
 ┌─────────────────────────────────────────────────────────┐
 │ HTTP 层        H1 / H2（帧预算）/ H3                    │
 │                JA4H · 请求头归一化                      │
 └─────────────────────────────────────────────────────────┘
     │
     ▼
 ┌─────────────────────────────────────────────────────────┐
 │ 响应缓存       命中 → 直接从工作进程内存返回            │──► 客户端
 └─────────────────────────────────────────────────────────┘
     │ 未命中
     ▼
 ┌─────────────────────────────────────────────────────────┐
 │ 过滤链（有序，遇 Deny 短路）                            │
 │   IP/ASN/地理 ACL → 信誉 → 限流 → 机器人评分            │
 │   → WAF（特征、语义 SQLi、Sigma）→ 蜜罐                 │
 │   → 分级验证 → 登录滥用 → 请求体扫描（ClamAV）          │
 └─────────────────────────────────────────────────────────┘
     │ 放行                          │ 拒绝
     ▼                               ▼
 ┌──────────────┐              ┌──────────────────────────┐
 │ 上游         │              │ 403 · 验证页面           │
 │ proxy_pass   │              │ 焦油坑 · 诱饵内容        │
 └──────────────┘              └──────────────────────────┘
```

每个阶段都可能短路。缓存命中发生在过滤链**之前**，这正是缓存模式的吞吐量大约是
转发模式两倍的原因。

## 横向状态层

| 层 | 作用范围 | 内容 |
|---|---|---|
| **单进程** | 一个进程 | 响应缓存、热点计数器、连接级状态 |
| **共享内存** | 同一主机的所有工作进程 | 分片原子计数器、信誉、限流令牌桶、评分状态 |
| **Redis（可选）** | 整个集群 | 跨节点信誉、分布式限流、集群视图 |
| **磁盘** | 持久化 | 配置、站点文件、蜜罐状态、拓扑、ML 模型、情报源 |

计数器按 CPU 分片以避免缓存行争用，并先在工作进程内批量聚合再合并到共享层。

## 两个数据面

`aegis-pingora`（基于 Cloudflare Pingora）是生产数据面，也是安装脚本部署的对象。
`aegis`（基于 Hyper）是旧版数据面与命令行工具，同时承载 HTTP/3 sidecar 监听器。

阅读代码时这一点很重要：只接入 `src/proxy/http.rs` 的过滤器**不会**作用于生产的
H1/H2 流量——那条路径在 `src/proxy/pingora_http.rs`。

## 信号、评分与动作

Aegis 刻意把三件事分开：

1. **信号** —— 指纹、信誉查询、异常检测、ML 评分。代价低、始终计算、本身从不拦截。
2. **评分** —— 把信号按 IP / JA4 / ASN 聚合并随时间衰减。
3. **动作** —— 只有它们会拦截：过滤器 `Deny`、下发验证挑战、调用处置器
   （XDP 拒绝、nftables 丢弃、BGP RTBH 通告、抬升验证下限），且都带自动回滚 TTL。

这就是为什么「可疑的 User-Agent」本身不会产生 403：它只是抬高评分。拦截决策来自
明确的规则与阈值，从而让误报可控。

## 管理面

管理监听器是独立的绑定（默认 `:6280`），提供：

- `/admin/ui` 上内嵌的 React 面板，
- `/admin/api/*` 下带令牌 RBAC（`admin` / `operator` / `read`）的 REST API，
- Prometheus 格式的 `/metrics`，
- 用于重载配置的 `/admin/reload`。

所有变更类调用都会写入审计日志。`/admin/api/*` 的变更操作一律 fail-closed：
未知路由要求认证，而不是放行。
