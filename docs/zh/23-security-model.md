# 安全模型

**语言：** **中文** · [English](../en/23-security-model.md) · [Русский](../ru/23-security-model.md)

本文说明 Aegis 防护什么、明确不防护什么、信任边界在哪里，以及已知的限制。
部分内容刻意写得并不好看——你无法依据一份营销描述来安全地部署一个安全代理。

## Aegis 防护的内容

| 威胁 | 机制 |
|---|---|
| L7 应用攻击（SQLi、XSS、路径穿越、RCE、LFI、SSRF、XXE、WebShell） | WAF：特征、语义 SQL 分析、多轮归一化、Sigma 规则集 |
| 自动化扫描与爬取 | 机器人评分、指纹一致性、蜜罐、焦油坑 |
| HTTP 请求洪水 | 限流、自适应突增检测、响应缓存、分级验证 |
| 慢速攻击（Slowloris、慢 POST） | 请求头与请求体读取超时、连接预算 |
| HTTP/2 帧滥用（Rapid Reset、超大请求头） | 监听器层面的帧限制 |
| 撞库 / 登录滥用 | 登录滥用检测、按路由的验证难度 |
| 容量型报文洪水（部分） | eBPF/XDP 内核丢包、按 IP 的报文与 SYN 预算、BGP RTBH 通告 |
| 恶意文件上传 | ClamAV 请求体扫描（可选） |

## Aegis 不防护的内容

- **链路饱和。** 如果洪水流量超过你的上联带宽，任何反向代理都无能为力——报文已经
  在你的线路上了。这正是 Aegis 支持 BGP RTBH 的原因：缓解必须发生在你的上游。
- **你自己应用中的漏洞。** WAF 提高利用成本，但不会修补你的代码。
- **已被攻陷的源站。** Aegis 保护通往源站的路径，而不是源站本身。
- **持有合法凭据的攻击者。** 授权是你应用自身的职责。

## 信任边界

```
   不可信 ───────────────────────────────────────────► 可信
   ┌──────────┐   ┌────────────┐   ┌────────────┐   ┌──────────┐
   │ 客户端   │   │ Aegis      │   │ 管理面     │   │ 源站     │
   │ 请求     │──►│ 数据面     │──►│            │   │ 后端     │
   └──────────┘   └────────────┘   └────────────┘   └──────────┘
    完全敌对       解析敌对输入     仅限已认证运维    默认可信
```

1. **来自客户端的一切都是敌对的** —— 请求头、请求体、TLS 参数、Cookie、指纹。
   指纹尤其**由客户端控制**：JA4 可以伪造。Aegis 把指纹当作信号，并支持运维显式
   配置的指纹拒绝规则，但不会仅凭指纹授予特权。
2. **管理面是独立监听、独立信任级别。** 它不受数据面过滤器保护，其安全性来自认证、
   RBAC 和**网络位置**。
3. **源站被数据面视为可信** —— 这正是下面「转发的客户端 IP 头」一条重要的原因。

## 加固清单

- [ ] **管理端口不在公网上。** 把 `:6280` 绑定到管理网口，或通过 VPN / SSH 隧道访问。
      这是本清单中最重要的一条。
- [ ] 已修改初始生成的面板密码；已轮换管理 API 令牌。
- [ ] 按角色分发不同令牌——不要为了读指标而发放 `admin` 令牌，应使用 `read` 角色。
- [ ] 审计日志已外送（`audit_log_path`）。
- [ ] 使用正式 TLS 证书，而非引导用的自签名证书。
- [ ] 开启 `cookie_secure`，所有站点通过 HTTPS 提供服务。
- [ ] 源站**只能**从 Aegis 访问（防火墙或私有网络）——可被直接访问的源站会让整个
      代理对攻击者而言变成可选项。
- [ ] 你的源站**不**盲目信任 `X-Forwarded-For`（见下）。
- [ ] 主机 SSH 已加固：仅密钥登录、禁用口令、fail2ban、防火墙。
- [ ] 限流阈值按真实流量调优，而非保持默认值。
- [ ] 面向浏览器的站点启用分级验证，API 站点关闭。
- [ ] 对拒绝流建立日志审阅或告警——从不查看的防护就是无法调优的防护。

## 已知限制

以下为当前状态，有些是刻意取舍，有些尚未闭环。列出它们是为了让你在部署中做补偿。

### 转发的客户端 IP 头（当前行为，非限制）

Aegis 会在每个发往上游的请求上，用自己解析出的客户端地址覆盖
`X-Forwarded-For` 与 `X-Real-IP`，并直接删除 `Forwarded`。客户端无法把伪造的地址
夹带到你的源站——即使把同一个头发送两次也不行。

源站收到的是单一地址而非链路。如果 Aegis 部署在 CDN 或负载均衡之后，请把该跳写入
`AEGIS_TRUSTED_PROXIES`：只有这样入站的 `X-Forwarded-For` 才会参与真实客户端解析，
并且最终转发出去的是解析后的地址。

### 信任令牌是持有型令牌

通过分级验证后会签发信任 Cookie（`aegis_fp`）。它**刻意不**与客户端 IP 绑定，
以免 CDN 后方或频繁切换地址的移动网络用户被反复验证。代价是：被窃取的令牌可以在
其它主机上重放。

**补偿措施：** 对高价值站点缩短信任 TTL。注意信任并不会关闭 WAF 或限流——它短路的是
验证挑战，而不是请求检测。

### 已获得的信任以 IP 为键

长时间表现正常的客户端会被提升到受信任层级，在 TTL 内跳过限流与验证。有耐心的攻击者
可以先「养」好一个 IP 再使用。一次拒绝即可撤销该信任，且 WAF 始终运行。

### 风险引擎为观察模式

ML 风险引擎会计算并上报评分，但其决策不会作为拦截强制执行——真正的拦截来自过滤链。
即使把引擎配置为强制模式，也请把评分当作遥测，而不要假定它在拦截。

### HTTP/2 帧预算仅部分覆盖

并发流、请求头列表大小与待处理 reset 的限制已在监听器层面生效（覆盖 Rapid Reset 与
超大请求头类攻击）。目前尚无针对 SETTINGS/PING 洪水的每连接专用预算。

### GraphQL 防护

查询深度、内省与批量限制已实现，但尚未接入生产数据面。如果你前置 GraphQL API，
请在应用层强制深度与复杂度限制。

### `challenge` 规则会掩盖 `block` 规则

WAF 采用首个命中优先。导入的 Sigma 规则集中同时存在 `block` 与 `challenge` 两种动作，
因此一条中危 `challenge` 规则若先命中某个载荷，就会盖过后面的高危 `block` 规则；
而当该站点未启用分级验证时，`challenge` 会退化为放行。

**补偿措施：** 在面向浏览器的站点启用分级验证，并把该规则集视为纵深检测，而不是
「某个载荷一定会被拦截」的保证。手写的特征层（SQLi、XSS、路径穿越、RCE）不受影响，
它们直接拒绝。

### 请求体检测有大小上限

请求体按配置上限扫描（默认 1 MiB），超出部分会在不经 WAF 检测的情况下转发。
如果大请求体对你的威胁模型重要，请调高上限或在源站限制上传路径。

### XDP 需要能力与兼容内核

在 6.x 内核上缺少 `CAP_PERFMON` 时 eBPF 程序会加载失败，Aegis 将静默回退到用户态
过滤——防护仍然有效，只是没有内核快速路径。请检查启动日志，不要想当然认为 XDP
已启用。
