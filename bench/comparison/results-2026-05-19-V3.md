# V3 — Aho-Corasick WAF + JA4H alloc fix (2026-05-19)

## Что добавилось поверх V1 (Q1+Q3+Q5+Q6+Q7+Q2a)

### M2 — Aho-Corasick для WAF сигнатур
- 75 паттернов из 5 категорий собираются в один automaton при `WafFilter::new()`
- `match_signature()` теперь делает **один проход** O(n) вместо 75 вызовов
  `s.contains(p)`
- Категории остаются индивидуально-отключаемыми (`disable_signatures`)
- Fast-path через `find()` без аллокации iterator-state
- Slow-path через `find_iter()` только если у первого матча категория
  в `disabled`
- Auto kind вместо DFA — DFA-таблица била по L1 кешу на коротких входах
- 6 новых тестов добавлены (canon + сам автомат)

### JA4H — `Vec<&str>` вместо `Vec<String>` для header names
- `HeaderName` гарантировано lowercase per http-crate invariants
- Убрал `.to_string()` × N для каждого заголовка в запросе
- Cookie: `Option<&str>` вместо `Option<String>`

## Что выяснилось по пути

1. **DFA-kind Aho-Corasick был хуже** на коротких входах (~75 коротких
   ASCII-паттернов, инпут 30–60 байт): большая state-table бьёт L1.
   Auto-kind (ContiguousNFA) — заметно быстрее. Зафиксировано в коде
   комментарием.

2. **`find_iter().next()` тяжелее `find()`** на ~1µs из-за iterator
   state. Hot-path теперь использует `find()`, fallback на `find_iter`
   только если категория первого матча отключена.

3. **Прирост от Aho-Corasick на голом GET-пути мал** (~0%) — там canon
   возвращает `Cow::Borrowed`, паттерны не находятся, и линейный
   `contains` уже векторизован компилятором. Реальная выгода — на
   WAF-active пути (+3% над V1) и в теории на POST с большим телом
   (масштабируется как O(n) против O(n·k)).

4. **Архитектурно-важная победа**: добавление новых сигнатур теперь
   стоит O(1) per-request, а не O(k). Можно безбоязненно расти до сотен
   паттернов.

## Что осталось из плана (для будущих ускорений)

| Идея | Effort | Ожидание | Почему не сделано сейчас |
|---|---|---|---|
| Arc<HeaderMap> вместо clone | M | +3–5% | требует менять trait у всех фильтров |
| Per-CPU shard для scorer/anomaly | M | +2–5% на 100k+ RPS | можно сделать отдельно |
| Lazy `Uuid::new_v4` | S | +1% | нужен только когда tracing активен |
| Pingora migration | XL | +30–50% | отдельный квартал, ломает hyper |
| eBPF inline WAF | XL | +5–15% | требует расширения XDP программы |

## Итоговая позиция

- **+11% на WAF-нагруженном трафике** — реальная победа
- **+3–6% на голом проксировании** — реально, но скромно
- **0 регрессов в защите**
- **0 регрессов в тестах**

Aegis на чистом throughput всё ещё ~45% nginx — фундамент hyper vs
бесстековый C. Без pingora-миграции потолок уже близок.
Но **на смешанной защитной нагрузке** мы уже близко к насыщению CPU и
основной задел теперь в M3-M5 + L1, не в мелких аллокациях.
